# ADR-0001: 수집 → 전처리·구조화 → 스코어링 3단계로 나눠 구현

- 상태: 채택
- 날짜: 2026-10-12
- 관련 스펙: 전체

## 맥락

전체 흐름은 "사람인 이미지 공고 수집 → 이미지에서 조건 추출 → 지원자 매칭 점수"다. 세 부분은 불확실성의 종류가 완전히 다르다.

| 부분 | 주된 불확실성 |
|---|---|
| 수집 | 외부 사이트 구조 (iframe 경로, 셀렉터, 이미지 호스트) |
| 전처리·구조화 | 이미지 인식 품질, 요건을 직군 무관 구조로 표현하는 방법 |
| 스코어링 | 점수 모델, 근거의 신뢰성, 목업 데이터로 보정 |

먼저 전체 구조를 한 번에 짠 초안(스파이크)이 있었으나 실제 사이트·LLM으로 검증된 부분이 없었고, 이후 각 단계를 가장 단순한 형태로 한 번에 관통시키는 방식도 검토했다.

## 결정

세 단계로 나눠 **단계별로 스펙 → 구현 계획 → TDD 구현 → 실제 데이터로 관찰**을 끝낸 뒤 다음 단계로 넘어간다.

1. 수집 (crawler)
2. 전처리·구조화 (preprocessing)
3. 스코어링 (scoring)

- 단계 사이의 계약은 파일 산출물로 고정한다 ([ADR-0005](0005-origin-snapshot.md)).
- 다음 단계의 스펙은 앞 단계의 **실제 산출물**을 보고 쓴다. (예: 전처리 스펙은 실제 수집된 이미지의 크기·형태를 보고 슬라이싱 필요 여부를 정한다)
- 진입점(CLI·API·UI)은 단계와 직교한다. CLI 명령은 단계마다 추가하고, API·UI는 보여줄 결과가 생길 때 붙인다 ([ADR-0002](0002-thin-entrypoints.md)).

## 검토한 대안

- **한 번에 전체 구현 (스파이크)** — 빠르게 모양은 나오지만, 실제 사이트·LLM으로 검증되지 않은 가정이 모든 모듈에 퍼진다. 테스트가 사후에 붙어 설계를 이끌지 못한다.
- **최소 E2E 경로 먼저 (walking skeleton)** — 통합 문제를 일찍 발견하는 장점이 있지만, 단계마다 "가장 단순한 버전"과 "제대로 된 버전"을 두 번 만들게 되고, 각 단계의 산출물 형식이 계속 흔들린다.

## 결과

- 얻는 것: 단계마다 독립적으로 검토 가능한 산출물(스냅샷, 구조화 조건, 점수)이 남는다. 각 단계의 불확실성을 그 단계 안에서 해소한다. 커밋 이력이 단계별 판단 과정을 보여준다.
- 감수하는 것: 전체가 처음 이어지는 시점이 3단계 끝으로 늦어진다. → 단계 간 계약(파일 형식)을 각 단계 스펙에서 먼저 확정하고, 다음 단계는 그 파일만 입력으로 받게 해 통합 위험을 줄인다.
