# ADR-0005: 공고 원본을 스냅샷으로 보존하고 단계 간 계약으로 삼는다

- 상태: 채택
- 날짜: 2026-10-12
- 관련 스펙: 01

## 맥락

수집 단계는 아직 공고 내용을 구조화하지 않는다. 그래서 "만들 데이터 모델이 없다"고 볼 수도 있지만, 다음 이유로 **원본(오리진) 데이터와 그 출처 정보**는 수집 시점에 남겨야 한다.

1. **재현성** — 사람인 공고는 마감되면 사라지거나 바뀐다. 전처리·스코어링을 다시 돌리려면 그때 받은 원본이 그대로 있어야 한다.
2. **단계 간 계약** — 전처리 단계가 사람인 HTML 구조를 몰라도 되게, "이 공고의 본문 이미지는 이것들"이라는 정리된 입력이 필요하다 ([ADR-0001](0001-three-stage-delivery.md)).
3. **추적성** — 추출된 조건이 어느 이미지에서 왔는지, 언제 어디서 받은 것인지 거슬러 올라갈 수 있어야 한다. 운영 구조(고객사 경유 유입)에서 감사 근거가 된다.
4. **변경 감지** — 같은 공고를 다시 받았을 때 내용이 바뀌었는지 해시로 판단한다.

## 결정

공고 1건 = 스냅샷 디렉터리 1개.

```
data/postings/{site}/{posting_id}/
  snapshot.json      매니페스트
  view.html          공고 페이지 원본 바이트
  detail.html        상세 iframe 원본 바이트
  images/NN.ext      본문 이미지 원본 바이트 (재인코딩 안 함)
```

매니페스트(`PostingSnapshot`)에 남기는 것:

| 항목 | 이유 |
|---|---|
| `source` (site, method=`crawl`\|`upload`, posting_id, url) | 출처. `upload`는 운영 시 고객사 경유 유입을 같은 형식으로 받기 위한 자리 |
| `fetched_at` | 언제의 공고인가 |
| 파일별 `path`, `sha256`, `bytes` | 무결성, 변경 감지 |
| 이미지별 `source_url`, `format`, `width`, `height`, `index` | 원본 위치, 전처리 단계의 입력 판단(예: 세로 길이) |
| `skipped_images` | 받았지만 제외한 URL (아이콘·이미지 아님) — 누락 의심 시 확인용 |
| `title` | 사람이 공고를 식별하기 위한 페이지 메타데이터. **매칭 조건으로 쓰지 않는다** (조건은 이미지에서만) |
| `body_text_length`, `is_image_posting` | 이미지형 공고인지 판별 근거 |
| `schema_version` | 매니페스트 형식 변경 대비 |

규칙:
- 원본은 **바이트 그대로** 저장한다 (이미지 재인코딩·HTML 정규화 금지). 가공은 다음 단계의 일이다.
- 매니페스트는 모든 파일 저장이 끝난 뒤 **마지막에, 원자적으로** 쓴다. 매니페스트가 있으면 완전한 스냅샷이다.
- 공고당 최신 스냅샷 1개만 유지한다. 다시 수집(`--refresh`)하면 교체한다.

## 검토한 대안

- **이미지 파일만 저장** — 출처·시각·제외 내역이 없어 재현·추적이 안 된다.
- **수집 시점에 이미지를 가공(리사이즈·분할)해 저장** — 가공 방식이 바뀌면 다시 수집해야 한다. 가공은 전처리 단계의 결정으로 남긴다.
- **스냅샷 버전 이력 보존** (`{posting_id}/{fetched_at}/`) — 변경 이력 추적에 좋지만 현재 필요 없다. 해시가 있으므로 필요해지면 확장 가능하다.
- **DB(SQLite 등)에 저장** — 사람이 바로 열어볼 수 있는 파일이 검토·디버깅에 유리하고, 공고 수가 적다.

## 결과

- 얻는 것: 전처리 단계의 입력이 `PostingSnapshot` 하나로 고정된다. 원본이 남아 있어 이후 단계를 몇 번이든 다시 돌릴 수 있다.
- 감수하는 것: 원본 HTML·이미지를 레포에 커밋할지는 별도 판단이 필요하다 (재현성 vs 용량·저작권). 스펙 01에서는 커밋하는 쪽으로 두고 관찰 후 재검토한다.
