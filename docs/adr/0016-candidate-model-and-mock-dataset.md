# ADR-0016: 이력서는 반정형 JSON으로, 판정할 때 줄 번호 텍스트로 펼친다 — 목업 12건은 레포에 둔다

- 상태: 채택
- 날짜: 2026-10-12
- 관련 스펙: 03

## 맥락

- 지원자 데이터는 목업 이력서다. 공고 2건 × 6명 (완벽 2 · 부분 3 · 미스매치 1).
- 이력서를 스킬 목록으로만 만들면 매칭이 키워드 비교로 줄어든다. 공고 B(생산직)의 요건은 스킬이 아니라 거주지·근무 형태·경험이다.
- 판정 근거를 이력서 원문 인용으로 검증하려면(ADR-0015) 인용할 "원문"이 정해져 있어야 한다.
- 데이터셋은 제출물이고, 각 이력서가 무엇을 검증하려고 만든 것인지 드러나야 한다.

## 결정

1. **반정형 JSON**: 학력(수준·전공·졸업 상태·시기), 경력(기간·역할·서술), 자격증, 어학, 병역, **자기 신고**(입사지원서의 "입사 가능 시기", "교대 근무 가능" 같은 항목), 기술, 자기소개. 학력 수준과 경력 기간은 코드가 계산할 수 있도록 구조화하고, 나머지는 서술로 둔다.
2. **줄 번호 렌더링**: 판정 시 `L01 [학력] 학사 · … · 졸업 (2026-02)`처럼 한 줄에 한 사실로 펼쳐 LLM에 주고, 인용 검증도 이 텍스트에 대해 한다. 렌더링 함수가 이력서의 유일한 "원문"이다.
3. **`meta` 분리**: 대상 공고, 의도 라벨, 설계 의도, 의도한 판정은 `meta`에만 두고 렌더링·판정·점수 계산은 `meta`를 읽지 않는다 (테스트로 보장). CLI 결과 표에 라벨을 **표시만** 한다.
4. **위치**: `dataset/candidates/*.json` — 레포에 포함한다 (`data/`는 버전 관리하지 않음, ADR-0007).
5. **설계 원칙**: 같은 라벨 안에서도 지원자마다 **다른 판정 경로**를 검증하게 만든다 (같은 단어 / 다른 표현 / 기한 단서 / 대상 조건 / 확인 필요 / 키워드 나열 / 학력 서열).
6. **민감 정보 필드 없음**: 장애·보훈 여부, 생년·나이, 성별 필드를 두지 않는다 (ADR-0018). 병역은 국내 입사지원서의 일반 항목이라 둔다 — 여성 지원자는 "해당 없음"으로 쓴다.

## 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| 자유 텍스트 이력서 | 실제와 가깝지만 학력 서열·경력 연수를 코드로 계산할 수 없고, 렌더링 기준이 없어 인용 위치를 정하기 어렵다 |
| 스킬·키워드 목록 | 직군 일반화가 안 된다 (생산직 요건은 스킬이 아님). 키워드 나열에 속는지 검증할 수 없다 |
| 실제 이력서 파싱 (PDF) | 범위 밖 — 이 단계의 질문은 "매칭이 납득 가능한가"이고, 입력 형식이 아니다 |
| LLM으로 이력서 생성 | 빠르지만 "각자 다른 이유로 점수가 갈리게" 하는 설계 의도를 통제하기 어렵다. 의도표(스펙 03 7장)를 먼저 쓰고 손으로 작성한다 |

## 결과

- 얻는 것: 판정 근거를 줄 단위로 검증·표시할 수 있다. 데이터셋 자체가 테스트 설계 문서가 된다 (`meta.intent`, `meta.expected`).
- 감수하는 것: 실제 이력서와 형식이 다르다 → 운영에서는 이력서 파싱 단계가 같은 JSON을 만들면 된다 (스코어링은 그대로).
